Backend-Architektur

Das Backend von Smart Supply Pro ist ein Spring-Boot-Dienst für Lieferantenbeziehungen, Bestandsverfolgung und Bestandsanalysen. Es stellt dem React-Frontend eine REST-API bereit, hält seine Daten in der Oracle Autonomous Database und meldet Benutzer über Google an.

Dies ist eine Zusammenfassung der arc42-Dokumentation auf einer Seite. Jeder Abschnitt verweist auf die Seite mit den Details und Begründungen: Die vollständige Architekturdokumentation umfasst Einführung und Ziele, Randbedingungen, Kontext, Bausteine, Laufzeit, Verteilung, Konzepte, Entscheidungen, Qualität, Risiken und Glossar.

Kontext und Technologie

Der Browser spricht nie direkt mit dem Backend-Host. Er lädt das Frontend von www.smartsupplypro.de; dessen Nginx liefert das Bundle aus und leitet /api, die OAuth2-Pfade und /logout an api.smartsupplypro.de weiter. Dort beendet der Caddy des gemeinsam genutzten Hetzner-Hosts TLS und reicht die Anfrage an den Backend-Container weiter. Google ist der einzige Identitätsanbieter, die Oracle Autonomous Database die einzige Produktionsdatenbank.

Bausteine

Anfragen durchlaufen vier Schichten. Controller leiten weiter, validieren das eingehende DTO (@Valid) und tragen die Berechtigungsregel (@PreAuthorize); Services enthalten die Geschäftsregeln und die Transaktionen; Repositories speichern, mit eigenen Fragmenten für das Analyse-SQL. Entitäten verlassen die Service-Schicht nie, und DTOs erreichen die Repositories nie. Die Abbildung zwischen beiden ist schlichtes Java, ohne Generator.

Details: §5 Bausteinsicht, ADR-0002, ADR-0003.

Sicherheit

  • Anmeldung. Das Backend führt den Authorization-Code-Flow von Google selbst aus; der Browser hält nie ein Token. Nur E-Mail-Adressen auf der Freigabeliste können sich anmelden, und für alle anderen wird kein Konto angelegt (ADR-0011). Nach der Anmeldung führt das Backend eine Server-Session; ihr Cookie ist HttpOnly, Secure und SameSite=Lax.
  • Rollen. ADMIN darf alles; USER darf lesen sowie Mengen und Preise anpassen. Jeder /api-Endpunkt außer Health und /api/me trägt eine ausdrückliche @PreAuthorize-Regel, und ein Vertragstest schlägt für einen Endpunkt ohne Regel fehl.
  • Demo-Modus. Ist app.demo-readonly aktiv, darf ein anonymer Besucher die Demodaten lesen; jede Identität in einer Antwort wird durch ein Pseudonym ersetzt. Schreibzugriffe erfordern weiterhin einen angemeldeten USER oder ADMIN.

Details: §8 Querschnittliche Konzepte, §6 Laufzeitsicht, ADR-0007.

Fehler

Der HTTP-Status trägt das Ergebnis. Jede Fehlerantwort, auch die 401 eines nicht angemeldeten API-Aufrufs, hat dieselbe Form: ein Fehlerkürzel, eine Meldung und einen Zeitstempel, dazu fieldErrors, wenn der Fehler ein Eingabefeld benennt. Meldungen aus Ausnahmen werden bereinigt, bevor sie den Client erreichen; Stacktraces erreichen ihn nie.

Details: §8 Fehlerbehandlung, ADR-0004, ADR-0005.

Daten und Analysen

Oracle hält die Produktionsdaten; dort wendet Flyway die Schema-Migrationen an. Die automatisierten Tests laufen auf H2 im Oracle-Kompatibilitätsmodus, weil die Free-Tier-Datenbank nur freigegebene Adressen zulässt. Die Analyseabfragen liegen in eigenen Repository-Fragmenten, ihr SQL in Builder-Klassen; wo H2 und Oracle sich tatsächlich unterscheiden (Datumsgruppierung, Bewertung), hat jede Abfrage eine Variante je Dialekt.

Details: §8 Infrastruktur, ADR-0006.

Verteilung

Das Backend läuft als ein Container auf einem gemeinsam genutzten Hetzner-Host. Ein Merge nach main startet die Backend-CI; ist sie grün und betrifft die Änderung die Anwendung, wird das Image gebaut, auf behebbare Schwachstellen der Stufen HIGH und CRITICAL geprüft, in GHCR veröffentlicht und auf den Host ausgerollt, gefolgt von einem Health-Check. Das Datenbank-Wallet und alle Zugangsdaten kommen beim Start aus der Umgebungsdatei des Hosts, nie aus dem Image.

Details: §7 Verteilungssicht, ADR-0009, ADR-0012.

Qualität und Tests

Unit-Tests prüfen Services und Validatoren ohne Spring; Web-Slice-Tests prüfen die Controller mit ihren Sicherheitsregeln; Persistenztests führen jedes Repository gegen H2 aus; einige Tests mit vollem Kontext prüfen den Start. Die Browser-Testsuite prüft das Frontend gegen dieses Backend, gebaut aus demselben Commit, bevor etwas ausgerollt wird. Der Abdeckungsbericht des letzten Builds auf main ist veröffentlicht: Backend-Abdeckungsbericht.

Details: §8 Tests, §10 Qualitätsanforderungen.

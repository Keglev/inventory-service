Backend Architecture

Smart Supply Pro’s backend is a Spring Boot service for supplier relationships, inventory tracking and stock analytics. It serves a REST API to the React frontend, keeps its data in Oracle Autonomous Database and signs users in through Google.

This is a one-page summary of the arc42 documentation. Each section below points to the page that holds the detail and the reasons: the full architecture documentation covers introduction and goals, constraints, context, building blocks, runtime, deployment, concepts, decisions, quality, risks and the glossary.

Context and technology

The browser never talks to the backend host directly. It loads the frontend from www.smartsupplypro.de, whose Nginx serves the bundle and proxies /api, the OAuth2 paths and /logout to api.smartsupplypro.de; there, the shared Hetzner host’s Caddy terminates TLS and forwards to the backend container. Google is the only identity provider; Oracle Autonomous Database is the only production database.

Building blocks

Requests pass through four layers. Controllers route, validate the incoming DTO (@Valid) and carry the authorization rule (@PreAuthorize); services hold the business rules and the transactions; repositories persist, with custom fragments for the analytics SQL; entities never leave the service layer, and DTOs never reach the repositories. Mapping between them is plain Java, without a generator.

Details: §5 Building Block View, ADR-0002, ADR-0003.

Security

  • Sign-in. The backend runs Google’s authorization-code flow itself; the browser never holds a token. Only e-mail addresses on the allow-list can sign in, and no account is created for anyone else (ADR-0011). After the login the backend keeps a server session; its cookie is HttpOnly, Secure and SameSite=Lax.
  • Roles. ADMIN may do everything; USER may read and adjust quantities and prices. Every /api endpoint except health and /api/me carries an explicit @PreAuthorize rule, and a contract test fails for one that does not.
  • Demo mode. With app.demo-readonly on, an anonymous visitor may read the demo data; every identity in a response is replaced by a pseudonym. Writes still need a signed-in USER or ADMIN.

Details: §8 Concepts, §6 Runtime View, ADR-0007.

Errors

The HTTP status carries the result. Every error answer, the 401 of an unauthenticated API call included, has one shape: an error token, a message and a timestamp, plus fieldErrors when the failure names an input. Messages that come from exceptions are sanitised before they reach the client, and stack traces never do.

Details: §8 Exception Handling, ADR-0004, ADR-0005.

Data and analytics

Oracle holds the production data; Flyway applies the schema migrations there. The automated tests run on H2 in Oracle-compatibility mode, because the free-tier database admits only allow-listed addresses. The analytics queries live in custom repository fragments with their SQL in builder classes; where H2 and Oracle really differ (date bucketing, valuation), each query has a variant per dialect.

Details: §8 Infrastructure, ADR-0006.

Deployment

The backend runs as one container on a shared Hetzner host. A merge to main runs the backend CI; when it passes and the change touches the application, the image is built, scanned for fixable HIGH or CRITICAL vulnerabilities, pushed to GHCR and released to the host, followed by a health check. The database wallet and all credentials come from the host’s environment file at startup, never from the image.

Details: §7 Deployment View, ADR-0009, ADR-0012.

Quality and testing

Unit tests cover services and validators without Spring; web-slice tests cover controllers with their security rules; persistence tests run every repository against H2; a few full-context tests check the boot. The browser suite runs the frontend against this backend, built from the same commit, before anything is released. The coverage report of the latest build on main is published: backend coverage report.

Details: §8 Testing, §10 Quality Requirements.
